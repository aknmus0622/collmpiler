# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository state

Version 0.1 (`0.1.0` in the package files; `clp --version`). The design documents (written in Japanese) are still the bulk of the repo; `REFERENCE.md` (English) is the one page a spec author needs. The code:

- `packages/core/index.ts` — the vocabulary specs are written in (`DSL.md` §16.0 is the current shape). **Everything is a node with named children; a node's kind (`KINDS`) has either fixed fields or free-named entries, never both.** A name is born only as a key of a group declaration — `states([...])` / `states({ A: "sentence" })` → `State.A`, `conditions({ key: "sentence" | all(...) | not(...) })` → `If.key` (composites get their meaning automatically; IR `conditions` shows them), `data({...})` → `Data.x` / `Data.x.set(v)` (record fields continue: `Data.last.status`), `queries({...})` → `Query.q` or `Query.q({...}).as("name")` (`.answer`, fields continue), `effects({...})` → `Effect.E({...})` (`.onlyWhen(h)`), `calculations`, `invariants`, `types({...})`, `decisions({ name: [If.x.then({cells}), otherwise({cells})] })` → `Decision.name.column` / `.of(state)`, `commands({ Name: { fields } | "sentence" | userWord(...) })` → `Command.Name` (`.with({...})` in the interpretation), `parts(...)`, `input({...})`. Every other `{}` holds fields (a command: `description`, `input`, `output`, `route`, `from`, `onlyIf`, `asks`, `calls`, `cases`, and the outcome fields `goTo`, `set`, `emits`, `responds`, `adds`, `removes`, `does`, which written on the command happen in every case — W1); `[]` is a list of self-named nodes (`cases: [If.x.then({...}), otherwise]`); a plain value is shorthand for what its place expects (a sentence, a type, a constant; `{}` in a type's place is never a type). The outermost component is `service({ description, init, uses: [groups...], assets })`; `component` is the internal base kind and is not exported. `goTo` may be a decision column whose cells are state handles (W2). Types: primitives, enums of strings or numbers, `integer/number/string({...})`, `record`, `list`, `optional`, `oneOf({ variant: type })` (values are single-key records), `value()` (any JSON value). `kind(name, { fields, expand })` defines a user word (L2) expanded at load time (checked deterministic by expanding twice); the built-in `forwards` (`Part.items.Complete.forward({ missing })`) is one. The new tree is converted to the old internal node tree (`component` / `command` / `when` ...), then to the internal form (`layer1Of`, `interpretation`); `GRAMMAR`'s rows for user-facing kinds are built from `KINDS`, and `check` reports `unknown-field` with the position. `interpretation(Component, [items])` lists named nodes: groups, `Command.X.with({...})`, `Component.with({ init, uses })`, meanings (`Handle.means(fn)`); commands and cases it does not mention gain nothing (unification). Components contain components (`DSL.md` §14): `parts({ todos: Todos })` → `Part.todos.Add({...})` in `calls`, `many(Todo, by("id"))` → `Part.items.at(key).Complete()`, `adds: [Part.items.add(key, {...})]` / `removes`. Zero dependencies, and no reliance on `@types/node`. Tests: `packages/core/test/`.
- `packages/core/internal.ts` — the internal form the CLI works on, and what evaluates it: the Layer 1 value (`Layer1`: entries as `{ $description }` or `{ $fragment }`), `resolveComponent` (overlays an interpretation's structure on Layer 1 and collects every way the two disagree in `problems`), the internal references `ref.*` (handles produce the same `{ $ref, path }` values), `decisionTable`, the registry of interpretations per component (a `WeakMap`; `activate` picks one when two are loaded), `active()` (the binding being evaluated, which `Table.of` and `Calc.x.of` read), and `decide` / `calculate` / `matchCondition`. It used to be the public vocabulary (`compose`, `typed`, `structure: {...}`, type-level checks with `Problem<...>`); none of that is exported any more — do not reintroduce it. The 1.0 design (`DSL.md` §16.0: nodes, kinds with either fixed fields or free-named entries, unification, `[]` as `compose([...])` of self-named nodes) reuses the name `compose` with a different meaning and a field form that is not the old `structure: {...}` (handles, kind-checked); follow §16.0, not the old forms. **Checking moved from the type system to the tree**: the heavy type-level model was removed, `tsc` is only for completion and light errors, and the guards are the tree check, `resolveComponent`, the diagnostics of `extract.ts`, and the oracle runtime (which now stops when a meaning function reads a name the spec does not have — the replacement for typed `state` parameters).
- `packages/cli/bin/clp.ts` — the `clp` command (`pnpm clp <command>`; from a subdirectory `pnpm exec clp`). It checks the Node version, then loads only the chosen subcommand from `packages/cli/src/commands/`: `compile`, `interpret`, `apply`, `verify`, plus the internal `__compare`. Each command module exports `summary`, `usage` and `main(args)`; `clp <command> --help` prints `usage`, an argument error prints it with exit code 2.
- `packages/cli/src/`
  - `loader.ts` — the single `SpecLoader`. `listComponents` names the components in a specs directory (a name is the export name in kebab case, `Order` → `order`); `loadSpecs` reads one (`{ component }`, optional only when there is exactly one). It finds the Layer 1 component and its interpretation, and normalizes the resolved component into the internal `SpecModel` + behaviours form the rest of the CLI uses (a command that does not branch becomes a table with only `otherwise`). With no interpretation, or one that conflicts with Layer 1, there is no model: only `layer1` / `problems`, which `extract` reports. `layer1Hash` / `STAMP` implement the staleness check: an interpretation file records the hash of the Layer 1 it was derived from, and `loadSpecs` sets `stale` when they differ.
  - `extract.ts` — builds the IR by rearranging the resolved component, the decision tables and the interpretation's structure (all function-free data; nothing is executed), and reports what only shows once the two layers are merged (the tree check's findings, unknown names, references whose type does not fit, a missing / conflicting / stale interpretation) with readable Japanese messages. `schema.ts` — runtime checks on field types.
  - `target.ts` — the `Target` interface: everything that depends on the language the production system is written in. `target-typescript.ts` — the only implementation, assembled from the TypeScript-specific modules below (`generate.ts`, `check.ts` + `scan.ts`, `runtime.ts`, `mutation.ts`'s built-in strategy, `static-check.ts`'s `tsc`).
  - `layout.ts` — where production code and the test-side files go (`--out`, or `--src` / `--tests`), and the one definition of "which files are production code" (`isSource` / `sourceFiles`).
  - `generate.ts` — IR → test-side files. `runtime.ts` — PBT runtime (fast-check) called by the generated `verify.ts`, plus `selfCheck`, the spec-only simulation run before any agent.
  - `graph.ts` — checks that follow from the written structure alone, without running the spec (`DSL.md` §8): states that cannot be reached from `init` and commands that can never be executed are errors; effects never emitted, data never set and queries with input never asked are warnings. Run by `clp compile` and `clp apply` (not part of `extract`'s diagnostics). It cannot see what meaning functions read, so queries without input, calculations and decision tables are not reported as unused, and "a path exists but is never taken" stays with the checks that run the spec.
  - `strategy.ts` — how an agent session is launched (an external command). `gates.ts` — per-phase entry gate (isolated sandbox with allowlisted inputs) and exit gate (collect allowlisted outputs, checks, PBT). `request.ts` — the three phase-specific request texts. `loop.ts` — the design → wiring → implementation pipeline with feedback and restarts.
  - `check.ts` + `scan.ts` — mechanical checks on what the LLM wrote (imports and generated files only; adapter contents are unrestricted).
  - `typecheck.ts` — runs `tsc`; `typecheckSpecs` is the fixed, always-on check of the specs. `static-check.ts` — the swappable `StaticCheckStrategy` for what the agent wrote (the TypeScript one is `tsc`; `--static-check off` disables it). `assets.ts` — resolves asset declarations (files keep their relative path under `clp/assets/`; text goes inline into the request) from the component's `assets` (relative to the component file) and from `--asset`.
  - `interpret.ts` — has an agent derive the Layer 2 interpretation into `<name>.interpretation.draft.ts` (command `clp interpret`), and `accept`, which turns a draft into the reviewed file and stamps it. Separate from the implementation pipeline. With no interpretation it starts from a generated skeleton; with one that is stale or no longer fits it starts from that and asks for the minimal update; with one that fits it does nothing. `sessions: n` has further sessions interpret independently under the first one's vocabulary, each asked for a defensible but less obvious reading, and compares each with the first by running both (`compareSpecs` in `runtime.ts`, via `compare.ts` in a subprocess).
  - `mutation.ts` — the mutation gate: a swappable `MutationStrategy` (built-in literal mutation) plus `judge`, the pass rule owned by the gate. `guide.ts` — default design guidance embedded in the request.
- `examples/checkout-ts/` — the order example, complete in one directory: `specs/` holds `order.decisions.ts` and `order.component.ts` (Layer 1, written by a person) and `order.interpretation.ts` (Layer 2, derived); `src/` is production code written by an LLM agent from the IR; `clp/` is the generated test side. Do not hand-edit `src/` to make verification pass; rerun the loop. Most tests use these specs as their subject (`specsDir` in `test/support.ts`). There is no top-level `specs/` any more: every example keeps its specs next to what was generated from them, and `clp` run inside an example directory finds them by default (`--specs specs`).
- `examples/library-ts/` — a book loan, made with `clp` alone from a deliberately rough spec. Its `README.md` records how the spec became precise from what `clp interpret` reported (and one wrong turn, see `onlyIf` below). # as the oracle; --mutation auto|builtin|off and --static-check auto|tsc|off select those strategies (auto = the target's own);
# --target typescript selects the target language (the only one so far).
# --out puts production code in <out>/src and the test side in <out>/clp; --src / --tests name the two places

## Vocabulary

"Command" means what drives a component from outside (the blue sticky note of event storming); "effect" means what the component does to its dependencies. Older commits used `actions` / `tells` in the spec and `commands` for effects in the IR and the contract — do not reintroduce that. In Japanese text: コマンド / 副作用. "コマンド" can also mean a shell command (the agent's command, `commandStrategy`); context tells.

## What is being built

A "Specification & Verification Engine": specs are written as pure TypeScript data, compiled to a language-independent JSON IR, and used to generate property-based tests (PBT) that verify a production system from the outside. The platform deliberately owns *only* spec/verification and places no constraints on the target system's architecture.

The same thing goes by several names across the docs: `co-llm-piler` (repo), `clp` (the CLI command, the `@clp/*` package scope, the default test-side directory `clp/`, and the `CLP_*` environment variables). Older names that may still appear in history: `aac` (the previous name of all of those), "SpecForge" and `aac-engine-monorepo`.

## Architecture

Layers, from `SPEC.md`:

- **Layer 1 – Spec**: written by a person, no functions at all, as rough or as precise as the author likes. `decisions({ name: [If.x.then({...}), otherwise({...})] })` maps condition handles to rows of values (values only, `otherwise` mandatory, same columns in every row). `service({...})` describes one unit; `service({ description: "..." })` is the roughest form. One rule covers everything: a group (`states`, `data`, `queries`, `effects`, `calculations`, `commands`) is left out of `uses`, given as a sentence (`queries("...")`), or given as entries, and **every entry is a sentence, fields, or both** (`{ description, ... }`). Entries by group: `data` — its type, or `{ type, initially, description }`; `queries` — its answer's type, or `{ output, input, description, fresh, increasing }`; `effects` — `input({...})`, a sentence, or `{ input, description }`; `calculations` — `{ description, output }`; `commands` — the command fields (see `packages/core/index.ts` above). Layer 1 may write `set` / `emits` too (W11; the interpretation's are appended, and it cannot override a `set` Layer 1 wrote). Groups are exported, because the interpretation imports the same handles. A list of cases is a value, so a fragment shared by several commands is a variable. `assets` (a list of `file(path)`, `dir(path)`, `text(content)`, each with an optional `{ phases }`) is attached to the agent's requests — not part of the spec's meaning, so never emitted into the IR. An enum array pulled out into a variable should carry `as const`.
- **Layer 2 – Interpretation**: one `interpretation(Component, [ ... ])` call, **derived by an LLM and reviewed by a person, never hand-written** (to change it, make Layer 1 more precise and run `interpret` again). It lists named nodes in the same words as Layer 1, matched by name with what Layer 1 wrote: groups it declares for what it adds (`Data`, `IfAdded`, `CalcAdded`, a commands group when Layer 1 gave commands as prose), `Command.X.with({ fields })` (fields added to a command, or to its cases by condition: `cases: [If.x.then({ emits: [...] })]`), `Component.with({ init, uses })`, and meanings (`Handle.means(fn)` for conditions, calculations and invariants — the oracle, never in the IR). A command or case it does not mention gains nothing. Values are constants or handles; the structure contains no functions and goes into the IR. **It cannot override structure written in Layer 1** (`resolveComponent` reports every attempt; a group listed in Layer 1 is closed to new entries, except calculations and invariants, and `otherwise` in cases). An interpretation file that fails to load (it uses a handle Layer 1 no longer has) is reported as `bad-interpretation` for its component. Because an LLM wrote the file, it is checked before use — by the tree check (kinds and grammar), by the merge with Layer 1 (closed and open groups come from `KINDS` via `mergeRules()`; problems are reported by path, `commands.X.cases.<condition>.goTo`), by the leaf check (`leafCheck` in `core/index.ts`, code `incomplete`: every path of the merged tree ends in a leaf — a type, a meaning function for each sentence, `otherwise` once cases branch, and a structural outcome, or an explicit `nothing: true`, wherever Layer 1's prose says something happens; driven by `required` / `oneOfRequired` / `nonEmpty` / `requiredCases` in `KINDS`, so do not add per-group checks), by the diagnostics of `extract.ts` (unknown names, values and references of the wrong type), by the graph check (with `final: true` states declared, a non-final state no command leaves is `dead-end-state`; `clp interpret` checks with `clp compile --strict-added`, which makes unused vocabulary the interpretation added an error), and by running the spec (conflicting conditions, broken invariants, a meaning function reading a name the spec does not have). Conditions are hit-policy Unique: more than one true is a `RuleConflictError`, none true means `otherwise`. Conditions and calculations see `status`, remembered data, the answers of queries without input, command input, and the answers named in the command's `asks`, in one flat namespace, so those names must not collide (the loader rejects it). Invariants see only `status` and data, and verify the spec, not the implementation.
- **Universal IR**: flat, language-independent JSON built from Layer 1 plus the interpretation's structure (older docs call it "Layer 1.5" or "Layer 2.5"). Its keys are the same words the spec is written in (`init`, `data`, `commands`, `queries`, `effects`, `calculations` as `{ description, output }`, `invariants`, `from`, `onlyIf`, `when`, `goTo`, `does`, `set`, `emits` as `[{ effect, input, onlyWhen }]`, `responds`, `description`); keep it that way, so no mapping table is needed. Version 6 made this true (version 5 still had `{ is, type }` and `effects: [{ name, payload, when }]`); the internal form (`SpecModel`, `SpecOutcome`) keeps the old names and `extract.ts` translates. Descriptions stay in one `descriptions` table, because vocabulary entries are bare types. Observations recorded during verification (`{ state, effects: [{ name, payload }], output }`) are not IR and keep their shape. `model` holds the vocabulary (`queries` as `{ input, output }`), `behaviors` what each command does (including `asks`), and `descriptions` the prose about the whole component, its groups and its entries (`"queries.isMonthEnd"`). The IR must not depend on *where* something was written: the same content gives the same IR whether Layer 1 or the interpretation holds it.
- **Layer 3 – Verification**: PBT generated on the test side (fast-check for TS today; rapid/proptest planned). A trial is a sequence of commands from the initial state; failures shrink to the shortest sequence. The default is 5000 trials (`--runs`): with 200, about one seed in five never reached the example's 10,000-yen threshold in the state where it matters, and with 1000 a decision behind several independent query answers (`payload-check`) went unverified under most seeds — a wrong bound check survived the mutation gate. Raising the count is cheap because a broken implementation stops at its first failure; only passing runs scale. Replaying the command sequences found by spec mutation as fixed examples was tried and not adopted: it only covers decision-table cells (the survivor was inside a condition), and its keys depend on the meaning functions, which generated files must not.
- **Adapter Contract**: `TargetSystemAdapter` (`setupIsolation(ports)` / `teardownIsolation` / `executeCommand(command)` / `getCurrentState`) is the only boundary to the target system. The harness-owned `Ports` fakes answer `queries` (a query with an input is a function of that input) and record `effects`; there is deliberately no way to inject state into the system — states are reached by executing commands, and remembered data is never read back directly, only observed through later behaviour.

Roadmap (`PACKAGE.md` §5): Phase 1 (core, dynamic evaluation in Node with fast-check, the LLM implementation loop) is in progress; IR extraction was pulled forward from Phase 2 because the LLM needs it as input. Multi-language generators and Mermaid/observability follow in Phases 3–4.

## LLM as the compiler

The framework generates **test-side code only**; it never places types, signatures, or files in production code. The pipeline (`SPEC.md` §2.3): specs → spec self-check → IR → three TDD phases, each a separate agent session wrapped in an **entry gate** (temp directory outside the repo holding only that phase's allowlisted inputs) and an **exit gate** (audit the sandbox, copy only that phase's writable paths to `--out`, regenerate `ir.json` / contract / `verify.ts` there, run `check.ts`, then the phase's own check):

| Phase | Agent sees | Agent writes | Phase check |
| --- | --- | --- | --- |
| `design` | IR, guide, assets | `src/` skeleton (signatures; bodies throw `"not implemented"`) | type-checks; loads; quotes no spec sentence |
| `wiring` | adapter contract, skeleton — **not the IR** | `clp/order.adapter.ts` | type-checks; PBT must fail for the "not implemented" reason (red) |
| `implementation` | IR, skeleton, guide, assets — **not the adapter or contract** | `src/` bodies | type-checks together with the adapter (catches changed signatures); PBT passes (green); mutation gate |

A failed check goes into the same phase's next `REQUEST.md`; when a phase exhausts its attempts the whole pipeline restarts from `design` (the failing phase cannot be attributed mechanically).

The same pipeline serves new code and changed specs (`INCREMENTAL.md`); "new" is only the case where no production code exists yet. `planOf` in `loop.ts` decides which phases run from the state of the output: no production code, or a boundary (`init`, `states`, `commands`, `queries`, `effects`) that differs from the previous `ir.json` → all three; only the adapter missing → wiring, implementation; otherwise implementation alone. When production code already exists (`ctx.incremental`): the implementation phase first grades the code as it is (`verifyGate`, recorded as `attempt: 0`) and is skipped if that passes, otherwise the result goes into the first request; the requests ask to keep what exists; a restart from `design` does not delete the code. The wiring red check is "while any unimplemented marker remains in production code, the tests must not pass".

Invariants to preserve when changing this:

- What each phase may see is the mechanism, not a detail: the wiring phase never sees the IR (so the adapter cannot encode business decisions) and the design/implementation phases never see the adapter contract (so production code is not shaped by the harness). Do not add an input to a phase, and do not mention `ports` or the harness in the design/implementation requests or the default guide, without re-examining these two properties. The skeleton is the one channel between them; `gates.ts` rejects skeletons that quote spec sentences.
- The layout is data, not convention. Nothing outside `layout.ts` may assume `src/` or `clp/`: ask the `Workspace` for `paths.*` and use `sourceFiles` / `isSource` for production code. The sandbox mirrors the output's relative layout (so relative imports are identical in both); only `REQUEST.md` and assets always live in the sandbox's `clp/`, because agent commands point there. Production code is removed file by file, never by deleting the directory — test-side files may sit next to it — and `resolveLayout` refuses a `--src` that looks like a project root.
- Several components share the production code and each has its own test side, named by component (`clp/order.adapter.ts`; always, even with one component, so that adding a second never renames files). `implement` reconciles them one at a time; `ctx.others` carries the rest. Keep these properties: design and implementation see every component's IR, wiring sees none and no other component's test side; after a component's own tests pass, the settled others (on-disk IR equal to the current spec, adapter present) are run again and a failure is `regression` feedback; the static check of design and implementation includes the others' adapters, so a changed public signature is caught. Whose code something is is decided by use, not by authorship or a record: files and components are many-to-many, and the implementation gate asks the target which production code each component's verification executes (`Usage`; V8 coverage for TypeScript; a file is *used* when one of its functions ran, or, for a file without functions, when it was loaded). Two things follow. (1) Writable scope: an agent may change new files, files its component uses (shared or not — the regression check protects the others), files nobody uses, and inert files (types only); a change to a file that **only other components use** is undone and rejected as `out-of-scope`. (2) Mutation scope: break what this component executed; skip what another component executed; and break what *nobody* executed if it sits in a file this component uses or nobody uses. Never narrow (2) to "executed by this component" only: when an adapter takes over a decision, the production decision is no longer executed, and exactly that dead code must still be mutated (a test caught this). With the scope known, `judge` applies `mutation-ineffective` to shared code too; only a target that cannot report usage falls back to "everything is in scope, rule off when shared".
- The adapter skeleton and unimplemented production code must fail with different messages (`ADAPTER_NOT_WRITTEN` vs. the target's `notImplemented`); when they were the same, a wiring session that wrote nothing passed the red check.
- Do not add a mode for "new" versus "changed": express differences as state (what exists, what changed) read in `planOf`, so that every scenario stays one flow. The one axis that is not state — whether the agent may write production code at all (legacy code) — is not implemented; when it is, it belongs in `planOf` too (drop design and implementation, send mismatches to a person, never to the wiring phase).
- On repeated runs the wiring phase reads fully implemented production code, so the mutation gate is the only guard against decisions copied into the adapter. Do not weaken it for incremental runs.
- Isolation belongs to the gates, not to strategies. Nothing that points at the repo may enter the sandbox: no spec sources, no `verify.ts` (it contains the specs path), no repo paths in file contents or environment variables. A new strategy must not need to re-implement any of this.
- Production code carries zero constraints: no framework imports or types, no required naming, no required DI, no shared vocabulary with the spec. The adapter always adapts to the production code, so never restrict what the adapter may contain; whether business decisions really live in `src/` is established by mutation, not by inspecting the adapter.
- Anything you want the implementer to do about design goes into the default guide (`guide.ts`) or an attached asset (the component's `assets`, or `--asset` for a single run), which is advice and never a pass/fail rule. Neither may mention business rules. Assets go to the design and implementation phases unless phases are named; sending one to the wiring phase can undo that phase's blindness to the spec.
- `loop.ts` and `gates.ts` are a language-agnostic template: they may call the target language only through `ctx.target` (`Target`). Do not import `generate.ts`, `check.ts`, `runtime.ts`, or TypeScript file names into them. Conversely, what must stay out of a target and in the gates: isolation, which phase sees what, the sandbox audit, the red/green verdicts, the quoted-spec-sentence check, and the mutation pass rule. The interface was extracted from the TypeScript code and has not been validated against a second language; expect to adjust it when one is added (the hard part is `runTests`, since the oracle always runs in TypeScript).
- Type-checking the specs and statically checking the implementation are two different things that merely share `tsc` today. The spec check is part of the framework's guarantees (specs are always TypeScript) and must stay unconditional. The implementation check depends on the target language, is only an early-feedback layer (PBT decides pass/fail, and everything must still be caught without it), and is a strategy that returns violations; which files to check per phase and how to word the feedback belong to `gates.ts`.
- The mutation pass rule lives in `judge`, not in a strategy. A strategy only breaks code and reports which mutants survived; record which strategy ran in the result.
- Anything the framework only has to *judge* (conditions, calculations, invariants) is a sentence or name plus a function in the interpretation's meanings; anything it has to *generate* or match exactly (states, commands, inputs, queries, effects, numeric constraints, transitions) is data — in Layer 1 or in the interpretation's structure. Never allow functions into the component, a decision table, or the structure of an interpretation: the IR, and every other intermediate artifact, is derived from them without executing anything.
- A command may answer whoever executed it: `output(type)` declares the shape (one value, or `record({...})` whose fields may be `optional(...)`, meaning `null` when absent — the same rule as `null` cells, no fillers), and `responds(value)` gives the value in each case, written in Layer 1 or in the interpretation (Layer 1 wins, like `goTo`). A command that declares `output` must respond in every case, and only such a command may. The expected observation then holds `output` next to state and effects, the contract's `executeCommand` returns it, and the comparison of interpretations has an `output` aspect. Before this, a refusal could only be verified as "nothing happens", so an implementation that told the caller nothing passed. `model.outputs` and `responds` appear in the IR only for commands that answer; a spec without them has the IR and contract it had before. An output may be `oneOf({...})`: then `responds: { variant: value }`. `outputs` is part of the boundary. A value the spec does not determine (a generated id, a time) must come from a query and be passed on; there is no "any value" expectation.
- Types nest: `record({...})`, `list(type)` (compared in order) and `optional(type)` (`null` when absent) may appear wherever a type is written — data, inputs, query answers, effect payloads, calculation results, command outputs. How a list or record *changes* is deliberately not structure: it is a calculation (a sentence plus a function) whose result is stored with `set`, so no collection vocabulary is needed. `initially(value)` gives a data field its starting value; without it the field stays unset (`undefined` to meaning functions), as before. A component with neither `states` nor `init` is stateless and internally has the single state `READY` (`STATELESS` in `internal.ts`). The self-hosted `payload-check` judges shapes and flat values; whether a structured value fits a structured type is compared by Stage 0 and handed over as the fact `Judged { fits }` (outside its spec's domain, as `pipeline`'s limits are). Structured constants are not handed to `value-writer`.
- A dependency's answers can carry a promise: `fresh()` (never the same value twice) and `increasing()` (never less than before), for queries without input. The fakes keep it (`answersOf` in `runtime.ts`, with what was answered before carried in the simulation state), the contract states it, and the implementing agent is told to rely on it, not implement it. The increments of an `increasing` query are drawn around the numbers found in the spec, which is what makes "N seconds since it was issued" reachable with a realistic clock; without the promise the clock is an unrelated value at every step and such a threshold is `unobserved`.
- A dependency can fail (`mayFail: true` on a query, W8): the stand-in throws on one ask in four (per input for a query with input), and the spec says what happens with the condition `Query.x.failed` (an asked node's `.failed`), a composite like `all` / `not` (`{ failed: name }`, sentence `query "x" failed`) whose meaning is automatic. There is deliberately no priority for failures: conditions stay exclusive, so "refuse an invalid input before or after asking" is the spec's to say. Reading a failed answer is a spec error (found by `selfCheck`). Specs without `mayFail` draw the same random sequences as before (the step arbitrary only gains `failures` when needed) — keep that, or seeds of existing tests move.
- Surviving a restart is a component's observable property (`durable: true`, or `durable: Store` naming a store component, W7). A component that is or contains something durable is verified with restarts drawn between steps (one in six): the adapter's `restartSystem()` must start a new instance on the same `ports.storage` (a fresh file path the harness creates per trial and removes; the adapter cannot use `node:fs`, so the harness owns the location), and the expectation keeps the durable component's state (its parts and items too) and resets the rest; promises' records survive (dependencies do not restart). The contract gains `storage` and `restartSystem` only for such components. A store named by `durable:` is treated like a part in the pipeline (reconciled first, code used but not changed or mutated, IR not shown). Production code may import `node:sqlite`. Where the data lives in production is decided by the composition root only.
- String inputs also include strings whose length is next to a number found in the spec ("more than 100 characters is refused"); without it, spec mutation rejected a correct spec because no random string ever came near the limit.
- Input generation hints are advice, never pass/fail: `among(data, field)` picks an input from what the component currently remembers (three times in four), `string({ examples })` mixes in given strings, and `around` *adds* thresholds. Numbers and strings found in the meaning functions and decision tables are **always** tried; before, declaring `around` switched that off, which turned `around` into a place where a threshold was copied by hand.
- A query with an input is asked *about something*, and what it is asked about is part of the spec: the command asks it (`Query.q({ field: constant | input field | data }).as("answerName")`; internally `asks`), in Layer 1 or in the interpretation, and reads the answer by that name. A query without input needs no `asks` and is read by its own name. The harness draws, per step, one function per such query (`fc.func`: same input, same answer; a new step may answer differently — the same "environment at the time of the command" meaning as before), so answers do not depend on how an interpretation names them. Verification is deliberately asymmetric: **asking with an input the command does not list fails** (even if production code swallows the exception), while not asking, order and count are not checked — if the answer matters, not asking shows up as a wrong outcome. Before this, an adapter dropped the argument and nothing noticed whether the implementation asked about the right name. Residual risk: an adapter could substitute the right argument itself; the wiring phase never sees the spec, and mutation cannot catch it.
- Before any agent runs, the spec itself is mutated (`observability` in `runtime.ts`, run by `clp compile` and `clp apply` after the self-check, and therefore also inside `clp interpret`'s check): each decision-table cell is changed the way the mutation gate changes literals, and the spec is run to see whether any expected outcome changes. A value that never shows cannot be verified in an implementation, so the gate would reject a correct implementation or push the check out of it; that is a spec problem and must stop here, not after a dozen agent sessions. Three verdicts: `precondition` (only whether a command can be executed changes — error), `unobserved` (nothing changes under the verification seed nor under two more — error: unused column, filler instead of `null`, unreachable threshold), `rare` (nothing under the verification seed, something under another — warning; never fed back to an agent). Boolean cells are warnings at most, because the gate only fails on numbers and strings. Do not decide `unobserved` from one seed: a finished spec's threshold was missed by 3 seeds in 30, and as an error that sent an interpreting LLM into a loop of wrong fixes. The judgement is hand-written on purpose for now (a component version was built in a PoC and agreed 22/22, but the rule changed during the PoC); move it to Stage 1 once it has settled.
- A component with `parts` is verified by running its own spec and its parts' specs together (`simulator` in `runtime.ts` composes child simulators; part state is carried inside the outer state). What is observed is the outer answer and every effect on the outside world, the parts' included as `todos.<Effect>`; the parts' state is not. The parts' dependencies appear in the outer contract and ports as `todos.<name>` (`dependenciesOf` in `loader.ts`). In the pipeline it is reconciled after its parts; its design and implementation sessions do not see the parts' IR, only their production code; files the parts' verification uses (`partFilesOf` in `gates.ts`) may not be changed (restored and rejected as `out-of-scope`) and are never mutated; its default run count is 500 (`defaultRuns`). With `route(...)`, the contract tells the wiring agent how to drive it over HTTP (`:name` path segments are input fields, `body` is the JSON body, other fields the query string; the answer's `status`/`body` are the response; a path field is never generated as `"."` or `".."`, which HTTP cannot carry in a path — such a step is outside the spec, like `onlyIf`). Production code may import only the Node built-ins a server needs (`node:http`, `node:url`, ...; never `node:fs`).
- `from` and `onlyIf` put a situation *outside* the spec: nothing there is tested and production code need not handle it. A rule the code must enforce ("cannot borrow at the limit") written as `onlyIf` makes the check in production code dead as far as the tests can tell; the mutation gate then rejects it (`mutation-survived` on the limit) until the agent removes the check — a real run passed on its sixth attempt that way. Such a rule is an outcome: a `when` case with no `goTo` and no effects. Do not relax the gate for this; the request to the interpreting LLM says the same.
- An agent that does not end normally is not feedback either. `commandStrategy` throws `AgentFailure` when the command cannot be started, times out (`--agent-timeout <seconds>`, default 600), is stopped by a signal, or exits non-zero; the run stops at once and nothing the agent left is graded or copied. Before this, a missing command, an expired login or a rate limit looked like "the file is missing" and was sent back until every attempt and round was used up.
- Spec errors are never the implementer's problem. `selfCheck` (`runtime.ts`) simulates the spec alone before any agent runs, and a `SpecError` during PBT yields `status: "error"`, which stops the loop instead of becoming feedback.
- Money and other exact quantities are integers, with rounding spelled out in the calculation's `is` sentence; float arithmetic makes the oracle and a correct implementation disagree for no good reason.
- The interpretation is the oracle, and an LLM writes it, so three guards must stay: (1) `interpret` writes `*.draft.ts`, which `loadSpecs` ignores unless called with `{ drafts: true }`; a person accepts it. Drafts must never load by default. The one opt-in is `clp apply --drafts` (for unattended CI runs), which uses drafts as the oracle, logs a warning, and records `oracle: "draft"` in the result — keep all three, because in that mode the same misreading by the LLM passes undetected. `accept` refuses a draft with an open `// REVIEW:` (the interpreting agent's question) or `// REVIEW(clp):` (a disagreement between two sessions, written into the draft by `interpret`); a person resolves each by changing Layer 1 or by rewriting it as `// REVIEWED:`, which stays as the record. An accepted file with an open mark is `unreviewed-interpretation` and stops everything. Do not add a flag that accepts past open marks. (2) An interpretation whose recorded Layer 1 hash no longer matches is stale and stops everything (`stale-interpretation`); only decision-table cell values are left out of the hash, because they reach the IR without passing through the interpretation. (3) Layer 1 always wins: never let an interpretation override structure a person wrote, and never "fix" an interpretation by hand — the person's lever is Layer 1.
- The comparison of two interpretations is behavioural (same command sequences, compare expected state and effects), not textual, so the two may name conditions and calculations differently. Later sessions are given the first one's boundary (states, command names and inputs, queries, effects; without `around`, which leaked a number the first session had read from the prose) and must not change it; they must never see the first one's draft or each other's. They are asked for a defensible reading that is *not* the most obvious one: with the same request, four real sessions filled every gap identically and the comparison found nothing. Input generation mixes in the literals found in the meaning functions and the values of the decision tables (`literalsIn` in `runtime.ts`; also used by PBT and the self-check), because a free-text field compared with `"Gold"` is never exercised otherwise, and a threshold kept in a table (`lostAfterDays: 30`) never appears in a function. The second session reports something on almost every run, and part of it contradicts explicit prose: "no differences" is not a goal, and judging whether a reading is one the prose allows stays with the author. Known blind spots: a shared misreading, the vocabulary itself, and constants defined outside the meaning functions. Differences are searched per command *and aspect* (`runs`, `state`, `effect:<name>`, `order`), and the walk continues past an effect-only difference; with one search per command, a receipt-amount difference hid a coupon-condition difference in the same command.
- The agent sees the IR only. The interpretation's meaning functions are the oracle and must never be emitted into the IR or the request; interpreting the natural-language conditions is the LLM's job, and PBT judges it.
- Test cases are never LLM-written. Expected values come from evaluating the resolved structure with the meaning functions (`runtime.ts`).
- Generated files are a pure function of the IR (no timestamps, no versions); `check.ts` relies on byte-equality with a regeneration. The PBT seed is derived from the spec hash so verification is deterministic — in `clp apply` and, without `--seed`, in `clp verify` too (they used to differ: verify drew a random seed).
- Every diagnostic has one form, `severity[code] where: message`, and nothing about a spec is thrown: vocabulary errors the loader used to throw (name collisions, an `init` outside `states`, a table without `otherwise`) come back as `grammar` entries and are reported with the rest. Type errors in what was written (`min > max`, an empty enumeration, an `around` outside the range: `bad-type`) and decision columns with mixed kinds (`bad-decision`) are errors; a case that never held when the spec was run under three seeds is the warning `unreached-case` (`unreachedCases` in `runtime.ts`). A condition conflict names the command and its input, and the reproduction includes that last step.
- `--out` must sit where `@clp/cli/runtime` resolves (a workspace package like `examples/*`, or under `packages/cli/` as the tests do).
- Agent-facing text (`REQUEST.md`, check violations) is English; user-facing diagnostics are Japanese.

Types vanish at runtime, so anything the IR or PBT needs must be declared as a value (the component) with the type derived from it — never the other way round.

## Self-hosting

The framework runs twelve of its own parts on code generated from its own specs (`SELF_HOSTING.md`). With them, every *decision* in the framework's core path (which phase runs, what is reported, how a value is written) is made by generated code; what remains hand-written is glue without decisions (walking, copying, defaults, assembling JSON) and the kernel (I/O, the type-level API, the oracle runtime). Do not turn glue into components: tried on paper for the rest of IR assembly, the walker would be larger than the component. Keep these properties when extending it:

- **Stage 0 stays.** Every part that moved to Stage 1 keeps its hand-written version: `referenceDiagnostics`, `payloadDiagnostics` and `serialize` in `extract.ts`, `reconcileStage0` in `loop.ts`, `interpretStage0` / `acceptStage0` in `interpret.ts`, `verdictStage0` in `runtime.ts`, `graphReportsStage0` in `graph.ts`, `checkReports` and `leafReportsStage0` in `packages/core/index.ts`, `declaredReportsStage0` in `declared.ts`, `slotReportsStage0` in `slots.ts` (which replaced `payloadDiagnostics`), `typeTextStage0` / `queryNotesStage0` / `contractSectionsStage0` in `generate.ts` and `requestSectionsStage0` in `request.ts`. The contract is generated synchronously, so the Stage 1 text decisions for an IR are computed beforehand and registered (`planContract` → `registerContractPlan`, keyed by spec hash); without a registered plan the contract uses Stage 0. Pass records are per component: they hash the files reachable by relative import from the component's spec and interpretation (`roots`), so editing one self spec leaves the others on Stage 1; the code hash still covers all production code. `extract(input)` uses Stage 0 by default and stays synchronous; the entry points (`commands/compile.ts`, `loop.ts`) pass Stage 1 results in as `extract(spec, await references(spec))`. If generated code cannot be loaded or throws, a warning is printed and Stage 0 decides: the framework must be able to run in order to repair its own generated code (this happens for real while a component is being regenerated). `CLP_STAGE=0` forces Stage 0.
- **Stage 1 uses only code that passed, for the specs as they are now.** That production code is present does not mean it passed: the exit gate copies an agent's output before grading and does not take it back, and anyone can edit it. So `clp apply` writes a pass record next to the test side when every chosen component has passed (`clp/<name>.verified.json`, `verified.ts`: a hash of the spec files, a hash of all production code plus that component's adapter, and the list of files; nothing else, so grading the same thing again gives the same bytes), removes the records of the components it is about to grade, and writes none when an unreviewed draft was the oracle. `stage1Adapter` checks the record of `packages/cli/self` before loading and falls back to Stage 0 with the reason (no record, specs changed, code changed). Consequences to keep in mind: production code is shared, so the records are written together at the end and a run with `--component` leaves the others' records stale if it changed shared code (a plain `clp apply` re-grades and re-stamps, without an agent); and while the framework regenerates its own components it runs on Stage 0 until the whole run has passed. The records are version-controlled; after changing `self/specs` or `self/src`, run `clp apply` on it before committing.
- **Stage 1 is used through the generated adapter contract** (`self/clp/<name>.adapter.ts`, loaded by `stage1Adapter`), never by importing `self/src` directly. The contract follows from the spec, and the loop keeps adapter and production code consistent, so a regeneration that renames classes or methods cannot break the framework.
- **Both stages of a check receive the same events.** `referenceEvents` and `payloadEvents` walk the spec and yield the component's own commands (`EnterCommand`, `AllowFrom`, `GivenField`, `Constant`, ...). The walk is glue without decisions and is shared; only the decisions differ between stages. A structured value is never passed whole: a decision-table column or an enum-typed value is handed over one cell / member at a time as `Constant`, a value known only by its type as `Typed`, a dangling reference as `Unresolved`. User-facing wording (Japanese messages, including *why* a value does not fit) is added in `extract.ts` from the returned decisions, never by generated code.
- **Output is assembled the same way input is taken apart.** Effects carry flat values only, so `value-writer` writes one element per effect (`WriteConstant`, `WriteReference { text }`, `WriteWasState`) and the glue in `stage1Values` puts the pieces into the nested IR, keyed by the slot they belong to (`valuesToWrite`). String building has no vocabulary of its own: the prefix (`input:` ...) is a decision-table value, so the mutation gate can check it is decided in production code, and the joining is a calculation described in a sentence; PBT compares the emitted text character for character. String literals are mutated only when the spec fixes them: decision-table values, and constants written in `responds` or in an effect's input (`decisionValues` in `mutation.ts`). A component with none of those and no numeric or boolean literal has no mutants at all and fails `mutation-ineffective`; before output constants were added, the `todo-item` example (answers are strings, no table) failed six attempts this way.
- **The pipeline is the procedure turned inside out.** In `reconcileStage1` the generated state machine emits effects (`StartSession`, `GradeCurrentCode`, `DiscardCode`); the driver executes them (gates, agent) and answers with a command (`DesignChecked { passed }`, ...). Which phase starts, whether to retry, restart from design or give up is decided only by the state machine; the driver owns execution and carrying feedback into the next request. Anything outside the spec's domain — `--from`, limits outside 1..3 — is decided before the machine starts and goes to Stage 0, so a run never switches stage halfway. The result records who decided per component (`stages`).
- **`stage.test.ts` holds the three fixed-point checks**: Stage 0 and Stage 1 return the same decisions in the same order (broken and correct specs; many kinds of values; the same scripted pipeline runs under both); `clp compile` prints the same output under both; and the framework, running on Stage 1, re-grades a copy of its own components without calling an agent and reproduces the generated files byte for byte. Extend it whenever another part moves to Stage 1.
- **The completion condition is "rebuildable from nothing"** (`SELF_HOSTING.md` §3, `ROADMAP.md`): with `self/src` and `self/clp` deleted, `clp apply` alone rebuilds all of its components (four at the time) and the framework's tests pass on the result. This has been done with real agents (14 minutes, 13 sessions); it does not mean Stage 0 can go — Stage 0 is what runs while the rebuild is in progress. Moving further parts to Stage 1 is not part of the condition, and the decisions that produce a verdict (running PBT, `judge`, red/green, the sandbox audit) stay in the kernel on purpose: graded code must not grade. 1.0 moves them, and the oracle runtime too, only under the rules of `SELF_HOSTING.md` §10 (those components are always graded by Stage 0; verdicts of both stages are combined strictly, values must agree; the stage switch itself never moves). Do not move any of them without those rules in place. Agents arrange production code differently on every rebuild (flat files once, a directory per component the next time), so nothing — tests included — may assume file names under `self/src`.
- **Grading components follow R1–R5** (`SELF_HOSTING.md` §10.3; `R1_COMPONENTS` in `stage1.ts` maps each to its Stage 0 files). A `clp apply` that reconciles one grades everything with Stage 0 (`setGradingByStage0`); its pass record says `gradedBy` and carries the hash of its Stage 0 files, and `stage1Adapter` refuses a grading component whose record was not graded by Stage 0 or whose Stage 0 changed. Before such a record is written, `runCases` runs the human-kept case inputs (`self/cases/<component>.json`) through the new code and Stage 0 in a subprocess (`clp __cases`); any disagreement and no record is written; functions the cases never execute are reported. In normal use `grade` runs both and takes the stricter verdict, warning on a disagreement. Never let a grading component grade itself, and never add an option that bypasses these.
- **Rare reports must be reachable in 200 runs.** `stage.test.ts` re-grades every self component with 200 runs (the real default is 5000); a report that needs a coincidence of random strings (`duplicate`, `dead-end-state`) survives mutation there. Make the spec draw such inputs from what it remembers (`among(Data.x)`), and split rarely-valid enum inputs into their own command (`tree-check`'s `Stray`), rather than raising the runs. `runStage1` serializes calls (generated components keep module state).
- **Say only what can be observed.** The rebuilt `reference-check` had a surviving mutant in `errors + 1`: the spec counted errors although only "was anything reported" was ever observed. That is over-specification in the spec, not a weak test; the sentence was reworded, the interpretation derived again (the data became a boolean) and the code rewritten. Spec mutation finds this for decision-table cells, not yet for calculations or remembered data.
- **Passing verification does not license a replacement.** Verification says the code fits its spec, not that the spec says what the hand-written code did. The first `payload-check` spec compared kinds of values while the hand-written check compared values, bounds and enum members; it passed, and would have dropped diagnostics. Compare against Stage 0 first.

## Decision-table cells that are never used

A cell a row does not use is written as `null`, never filled with a placeholder value. A filler copied faithfully by the implementation is a value whose mutation changes nothing, so the mutation gate rejects it (this cost one implementation round on every run before `null` existed). A reference that actually reaches a `null` cell is a spec error: `runtime.ts` throws while resolving it, so `selfCheck` reports it before any agent runs. Do not weaken `judge` to tolerate fillers.

## Decided constraints for implementation

From `DISTRIBUTION.md`; these are settled decisions, not suggestions:

- **Node is the only allowed runtime dependency.** No Bun, Deno, single binaries, or Docker. No npm publishing for now — the git repo is the distribution channel.
- **No build step.** `.ts` files run directly via Node type stripping; `packages/cli/package.json` `bin` will point straight at `./bin/clp.ts`, shared through a pnpm workspace (`"@clp/cli": "workspace:*"`).
- **Node >= 22.18** (`.node-version` is to be `24`), enforced via `engines`, `engine-strict=true` in `.npmrc`, and a version guard at the top of `bin/clp.ts`.
- Because of type stripping: no `enum`, no `namespace`, and relative imports must include the `.ts` extension. Use `as const` + unions instead of `enum`.
- Node refuses to type-strip `.ts` whose real path is inside `node_modules`. A workspace link is fine; a git dependency or tarball install is not. This is why specs live in this repo (`examples/*/specs`, `packages/cli/self/specs`) for now, and it — not npm publishing — is the trigger for ever adding a build.
- **Keep third-party dependencies minimal** (`packages/core` must stay pure TS with none; `fast-check` in `@clp/cli` is the one accepted exception). Use `util.parseArgs` for CLI arguments.
- Resolve paths against `process.cwd()`, never the script location (the `.bin` shim runs with the caller's cwd).
- Keep all spec loading behind a single `SpecLoader` (`packages/cli/src/loader.ts`).
- **Output must be deterministic**: sorted JSON keys, fixed indentation and line endings. Generated file headers carry only `ir-version` and `spec-hash` — never timestamps or the CLI version. The integer, monotonically increasing IR version is the sole compatibility contract.

## The `clp` command

One entry point, four commands (`packages/cli/bin/clp.ts`). The order a person uses them in: write Layer 1 → `clp interpret` (derive, then `--accept`) → `clp apply` → `clp verify` at any time; after a spec change, the same order again.

| Command | What it does |
| --- | --- |
| `clp compile [specs]` | type-check and self-check the specs, print the IR |
| `clp interpret` | have an LLM derive the interpretation; `--accept` puts a draft into use |
| `clp apply` | bring production code and adapter into agreement with the specs (the pipeline). Without `--agent` it only verifies and regenerates the test side, and stops with a clear message where an agent would be needed |
| `clp verify` | run the generated tests against existing production code; changes nothing |

- The command is `apply`, not `implement`: it reconciles what exists with what is declared, and most runs write no production code. The library function is still `implement()`; older commits and docs say `implement` for the command — do not reintroduce it.
- `clp` spawns itself for checks that must run in a separate process (`clp compile` from `interpret`, `clp __compare`); never spawn a `src/` file directly.
- `clp generate` and `clp test` from the older plans do not exist: generation is part of `apply`, and `verify` runs the tests.
